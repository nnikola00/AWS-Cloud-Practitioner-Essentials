## 1. The big picture — purpose-built databases

AWS's whole philosophy in this module: **stop forcing every problem into one relational
database.** Pick the database whose *shape* matches your data's shape.

| Your data looks like… | Database type | AWS service |
|---|---|---|
| **Rows and columns** with relationships between tables | Relational (SQL) | **Amazon RDS**, **Amazon Aurora** |
| **Items with a unique key**, flexible attributes | NoSQL key-value | **Amazon DynamoDB** |
| **JSON documents** with changing structure | Document | **Amazon DocumentDB** |
| **Things connected to other things** (friends, transactions, routes) | Graph | **Amazon Neptune** |
| **Data you read constantly and need in microseconds** | In-memory cache | **Amazon ElastiCache** |

Plus one service that isn't a database at all: **AWS Backup**, which centralizes the backups
for all of them.

### 🧒 ELI5 — the right container for the job

You wouldn't carry soup in a cardboard box, or keep a goldfish in a backpack. Each thing needs
a container shaped for it.

- A **spreadsheet** (relational) is great when every single thing you're tracking has *exactly
  the same set of facts* — every coffee bag has a name, a size, and a price.
- A **big box of labelled envelopes** (NoSQL key-value) is better when each thing is different
  — one envelope has a birthday in it, another has a favourite drink, and that's fine.
- A **string board with pins and yarn** (graph) is what you need when what matters isn't the
  things but **how they're connected** — who is friends with whom.
- A **snack on your desk** (cache) is for what you reach for every five minutes. You *could*
  walk to the kitchen each time, but why?

## 2. Relational databases

**Relational databases store data in a way that relates it to other pieces of data**, and use
**structured query language (SQL)** to manage and query it. This stores data in an
**easily understandable, consistent, and scalable** way — great for applications requiring
**structured data management**.

AWS offers **fully managed** relational solutions that **remove the burden of database
administration** while maintaining high availability and security, supporting popular engines
like **MySQL, PostgreSQL, and Oracle** — which makes **migrating existing databases to AWS**
easier.

### Example: a restaurant inventory management system

Each record holds the data for a single item: product name, size, price, and so on.

| ID | Product Name | Size | Price |
|---|---|---|---|
| 1 | Medium roast ground coffee | 12 oz. | $13.95 |
| 2 | Single-origin whole bean coffee | 12 oz. | $21.95 |

**📌 The word "relational" is about the *relationships between tables*, not the rows.** The
power comes from being able to join tables: an `Orders` table referencing a `Customers` table
referencing a `Products` table, so you can ask "which customers bought single-origin coffee
last March?" in one query.

### 🧒 ELI5 — the classroom seating chart

A relational database is a **very strict teacher with a clipboard.**

Every student gets a row, and **every row must have the same boxes filled in**: name, age,
class, seat number. You can't decide one student's row will have "favourite dinosaur" in it —
if one student gets that box, *everybody* gets that box. This strictness is annoying, but it
means the teacher can answer questions perfectly: *"Which 9-year-olds sit in the front row of
Class B?"* — instantly, no mistakes.

The strictness is the feature. A **schema** is just that clipboard: the agreed list of boxes.

## 3. Amazon RDS — managed relational databases

**Amazon Relational Database Service (RDS)** is a **managed** relational database service that
handles **routine database tasks: backups, patching, and hardware provisioning**. It supports
multiple **database instance class types** optimized for **memory, performance, or I/O**.

**For data resilience:**

- **Multi-AZ deployment**
- **Automated backups**
- **Manual DB snapshots** — full backups of your entire database instance, useful for
  **point-in-time recovery** or **long-term data archiving**

**Security features:** **network isolation**, **encryption in transit**, and **encryption at
rest**. And you can **scale database resources vertically or horizontally** as needed.

### Supported database engines

**Amazon Aurora · MySQL · PostgreSQL · Microsoft SQL Server · MariaDB · Oracle Database**

💡 Memorize this list of six — "which engines does RDS support?" is a standard exam question,
and the usual wrong answers are **MongoDB** (that's DocumentDB) and **DynamoDB** (not
relational at all).

### Use cases

Web applications, enterprise workloads, and product inventories for e-commerce platforms.

### Benefits

Your notes list four headings with no bodies. Here's what each covers:

| Benefit | ⬛ What it means |
|---|---|
| **Cost optimization** | Pay-as-you-go with **Reserved Instances** for steady workloads; **stop/start** non-production databases; right-size the instance class instead of buying hardware for peak load. No licenses or servers to buy up front |
| **Multi-AZ deployment** | RDS keeps a **synchronous standby replica in a second Availability Zone**. If the primary fails, RDS **automatically fails over** to the standby — the DNS endpoint stays the same, so your application doesn't change. This is for **availability**, not performance |
| **Performance optimization** | Choose an instance class optimized for **memory, compute, or I/O**; add **read replicas** to offload read traffic; use **Performance Insights** to find slow queries. Scale up or out without rebuilding |
| **Security controls** | **Network isolation** (the database sits in a private subnet in your VPC, reachable only by your application), **encryption in transit** (TLS), **encryption at rest**, plus IAM authentication and automated patching |

### 📌 The distinction the course glosses over: Multi-AZ vs. read replicas

These are both "extra copies of your database," and they are constantly confused.

| | **Multi-AZ standby** | **Read replica** |
|---|---|---|
| Purpose | **High availability / disaster recovery** | **Performance** — scale out reads |
| Replication | **Synchronous** | **Asynchronous** (may lag slightly) |
| Can you read from it? | **No** — it sits idle until needed | **Yes** — that's the whole point |
| On primary failure | **Automatic failover** | Manual promotion |
| Where it lives | A **different AZ** | Same AZ, different AZ, or a **different Region** |

💡 **Exam phrasing:** "improve **availability**" or "survive an AZ failure" → **Multi-AZ**.
"The database is slow because of too many **read** queries" → **read replicas**.

### 🧒 ELI5 — the teacher's assistant

You still have the strict teacher with the clipboard (§2) — but now the school has hired
someone to do the boring parts. They photocopy the clipboard every night (**automated
backups**), fix the broken pen (**patching**), and get a bigger desk when the class grows
(**hardware provisioning**).

And there's a **second teacher in the next room copying down every single word in real time**
(**Multi-AZ standby**). If the first teacher faints, the second one walks in holding an
identical clipboard and the lesson continues. The kids don't even notice.

That's RDS: **the same strict database you already know, with someone else doing the chores.**

### 🏢 Real example

An e-commerce site runs on MySQL. Self-managed on EC2, someone on the team must patch MySQL,
schedule `mysqldump` backups, test restores, configure replication, and be on call when the
disk fills. On **RDS with Multi-AZ**, AWS does all of it: nightly automated backups with
point-in-time recovery, patching during a maintenance window you choose, and automatic
failover to the standby in another AZ if the primary's hardware dies. The team goes back to
writing features.

## 4. Amazon Aurora

**Aurora** is a managed relational database **designed to help reduce unnecessary I/O
operations**. It is **compatible with MySQL and PostgreSQL**, provides **high performance and
availability**, and **automatically scales alongside your workloads**. It **replicates data
across multiple Availability Zones** for enhanced durability and fault tolerance, and features
**automated backups, encryption at rest, and continuous monitoring**.

### Use cases

Gaming applications, media and content management, and real-time analytics.

### Benefits

| Benefit | ⬛ What it means |
|---|---|
| **High performance and availability** | AWS rebuilt the storage engine from scratch: Aurora delivers up to **5× the throughput of standard MySQL** and **3× of PostgreSQL** on the same hardware, by eliminating wasted I/O. Availability comes from replicating across **three AZs** with automatic failover in typically under 30 seconds |
| **Automated storage and backup management** | Storage **grows automatically in 10 GB increments up to 128 TiB** — no provisioning or resizing. Backups are **continuous and incremental to S3** with no performance impact, enabling point-in-time restore to any second in the retention window |
| **Advanced replication and fault tolerance** | Aurora keeps **six copies of your data across three Availability Zones**. It can lose **two copies without affecting writes** and **three without affecting reads**, and self-heals corrupted blocks automatically. Up to **15 read replicas** share the same storage, so they lag by milliseconds rather than seconds |

### 📌 Aurora vs. "plain" RDS engines

Aurora is *offered through* RDS, but it isn't just "RDS with MySQL on it":

| | **RDS (MySQL/PostgreSQL)** | **Aurora** |
|---|---|---|
| Storage engine | The standard open-source one | **AWS's own distributed storage layer** |
| Data copies | 1 primary + 1 standby (Multi-AZ) | **6 copies across 3 AZs** |
| Storage scaling | You provision and resize | **Automatic**, to 128 TiB |
| Read replicas | Up to 5, replicating asynchronously | Up to **15**, sharing the same storage |
| Throughput | Baseline | Up to **5× MySQL / 3× PostgreSQL** |
| Cost | Lower | **Higher per hour**, often cheaper per unit of work |

💡 **Exam signal:** if a question wants **MySQL or PostgreSQL compatibility** *plus* the
**highest performance, availability, or automatic scaling**, the answer is **Aurora**. If it
emphasizes **lowest cost** or a **specific engine like Oracle or SQL Server**, it's **RDS**.

### 🧒 ELI5 — the same book, a better printing press

Aurora speaks the **exact same language** as MySQL and PostgreSQL — your application can't
tell the difference, the way a book reads identically whether it was printed on an old press
or a new one.

But underneath, AWS threw away the old press and built a new one. Instead of one librarian
carefully copying the book twice, **six scribes in three different buildings** each keep a
copy, checking each other's work. Two scribes can go home sick and the book is still being
written. And the bookshelf **grows a new shelf by itself** whenever the book gets longer.

## 5. NoSQL databases

**NoSQL databases** are sometimes called **non-relational** because their structure differs
from relational databases like RDS. Instead of **row and column relationships**, they build
structure using **key-value pairs**: data is organized into **items identified by unique
keys**.

Each key has **one or more associated attributes (values)** representing characteristics of
the data. **You can think of a key as a word entry in a dictionary, and the value as its
definition.**

> **Not every item in the table has to have the same attributes, and you can add or remove
> attributes at any time.**

That sentence is the entire point of NoSQL. Hold onto it.

### Example of key-value data

| Key | Value |
|---|---|
| **1** | Name: John Doe · Address: 123 Any Street · **Favorite drink: Medium latte** |
| **2** | Name: Mary Major · Address: 100 Main Street · **Birthday: July 5, 1994** |

Notice: item 1 has a favorite drink and no birthday; item 2 has a birthday and no favorite
drink. **A relational database could not do this** without an awkward mostly-empty column for
every possible attribute.

### Relational vs. NoSQL

| | **Relational (SQL)** | **NoSQL** |
|---|---|---|
| Structure | Tables of **rows and columns** | **Items** with keys and flexible attributes |
| Schema | **Fixed** — defined up front, changing it is a migration | **Flexible** — add or remove attributes anytime |
| Query language | **SQL**, with joins across tables | Key lookups and APIs; joins are avoided |
| Scaling | Usually **vertically** (a bigger machine) | **Horizontally** — spread across many servers |
| Strength | **Complex queries** and guaranteed consistency across related data | **Massive scale** with **predictable low latency** |
| Weak spot | Harder to scale out; rigid structure | Ad-hoc queries and multi-table relationships |
| AWS services | RDS, Aurora | **DynamoDB** (key-value), **DocumentDB** (document) |

### 🧒 ELI5 — the strict teacher vs. the box of envelopes

The relational teacher (§2) insists every student's row has the **same boxes**. If one kid
brings in a pet fact, every kid gets an empty "pet" box forever.

**NoSQL is a big box of envelopes with names written on the front.** Open John's envelope:
there's his address and his favourite drink. Open Mary's: her address and her birthday.
**Nobody cares that they're different.** Want to add "favourite dinosaur" to just one
envelope? Done, right now, no permission needed.

The trade-off: the strict teacher could instantly answer *"which 9-year-olds are in the front
row?"* The envelope box can't — you'd have to open every single envelope. **So NoSQL is
brilliant when you know exactly which envelope you want, and poor at browsing.**

## 6. Amazon DynamoDB

**DynamoDB** is a **fully managed NoSQL** database providing **fast and predictable
performance** for both **document and key-value** data structures. It's **powerful and
incredibly fast** for use cases requiring a **flexible schema**, and ideal for applications
needing **high performance and seamless scaling**.

It **scales seamlessly alongside your data without impacting performance**, so **you pay only
for the resources you use**. It includes **built-in security features** and **automatically
spreads your data across multiple servers** to handle your workload.

**📌 "Fully managed" here means more than RDS's version of it:** with DynamoDB there is **no
database instance at all** — no instance class to pick, no version to patch, no storage to
provision. It's the serverless end of the database spectrum.

### Use cases

Gaming platforms, financial service applications, and mobile applications with global user
bases.

### Benefits

| Benefit | What it means |
|---|---|
| **Scalability with provisioned capacity** | Automatically scales **throughput up or down based on actual usage**, ensuring consistent performance **without manual intervention**. You can specify **target utilization levels** and DynamoDB provisions capacity to maintain them. **No practical limits** on table size or data stored |
| **Consistent high performance** | **Single-digit millisecond response times at any scale**, maintained by automatically distributing data across **multiple servers and SSDs** |
| **High availability and durability** | **99.999% data availability** by replicating data across **three distinct facilities within each AWS Region**, plus the option of **multiple copies in separate Regions** for built-in fault tolerance and durability — continuous operation even if individual facilities fail |
| **Data encryption** | Comprehensive encryption **at rest and in transit**. All data is **automatically encrypted** before being written to the storage layer, with the flexibility to **choose between different kinds of encryption keys** |

**📌 Two sharpenings on that table:**

1. **Capacity has two modes**, and the notes only describe one. **Provisioned** (you set a
   target and it auto-scales within bounds) and **On-demand** (you set nothing at all and pay
   per request). On-demand is the right default for unpredictable traffic.
2. **Cross-Region copies are not automatic** — that's the **Global Tables** feature, which you
   turn on. By default your data is replicated across three facilities **within one Region**.

### 🧒 ELI5 — the magic locker room

Imagine a locker room where **every locker's key is a name**. Say "Mary's locker" and the
right door pops open in **less than the blink of an eye** — and it's *just as fast* whether
there are 10 lockers or 10 billion.

Three things make it magic:

- You never asked anyone to **build** the lockers. Bring more stuff and more lockers simply
  exist. Take stuff away and they quietly disappear, and you're only charged for what you used.
- Every locker's contents are **copied into three separate buildings**, so a fire loses nothing.
- Every locker can hold **completely different things**. Nobody inspects them for consistency.

The one catch — the same one as the envelope box: it's instant if you know **whose** locker
you want. *"Which lockers contain a red hat?"* means opening all of them.

### 🏢 Real example

A mobile game has 40 million players. Every player has a profile: level, coins, inventory,
achievements — and newer players have fields older accounts never had. At the launch of a new
season, traffic goes from 5,000 to 900,000 requests per second in ten minutes.

DynamoDB handles this because: the **key** is the player ID (every lookup is a direct hit), the
**schema is flexible** (new fields need no migration across 40 million rows), and capacity
**scales automatically** rather than requiring someone to pre-provision a bigger database the
night before. A relational database would need heavy sharding work to survive the same spike.

## 7. In-memory caches — Amazon ElastiCache

### What an in-memory cache is

An **in-memory cache** is a **high-speed storage layer** that temporarily stores **frequently
accessed data in RAM**. Retrieving from RAM is **extremely fast — often hundreds or thousands
of times faster than disk-based storage**.

**How applications use it:** when they need information, they **check the cache first** before
requesting it from the original data source. This **reduces load on primary databases** and
**speeds up response times** for end users.

**Ideal contents:** **session data, API responses, database query results**, and other
information applications need **repeatedly**.

```
   WITHOUT a cache                    WITH a cache
   ───────────────                    ────────────
   App ──► Database                   App ──► Cache ── hit? ──► return (microseconds)
           (every single time)                   │
           ~10-50 ms each                        └── miss? ──► Database ──► store in
                                                                cache ──► return
   1,000,000 identical queries        1 database query.
   = 1,000,000 database reads         999,999 cache hits.
```

### Amazon ElastiCache

**ElastiCache** is a **fully managed in-memory caching service** built to **reduce the
complexity of administering in-memory caching systems**. You **continue to use the same
Redis, Valkey, or Memcached tools and configurations** to scale your workloads. It
**automatically detects and replaces failed nodes**, making it ideal for applications needing
**consistent high performance**.

### Use cases

**Session data management**, **database query enhancement**, and **gaming leaderboards**.

### Benefits

| Benefit | What it means |
|---|---|
| **High performance for Redis, Valkey, or Memcached** | Streamlines deployment and maintenance of in-memory caching environments, with high availability, by automatically handling **hardware provisioning, software patching, and monitoring**. **Seamless scalability** — add or remove nodes as demand changes |
| **High availability** | Constantly monitors **primary nodes** for failures. When issues are detected it **promotes a replica to become the new primary without manual intervention**, typically completing recovery **within minutes** |
| **Replication across multiple AZs** | **Automatic replication across multiple Availability Zones** to protect against infrastructure failures. You configure primary and replica nodes **across different AZs** per your durability requirements, so **data remains accessible even if one zone has an outage** |
| **Data encryption** | **At-rest encryption** protects data in disk storage and automated backups. **In-transit encryption** secures data between clients and cache nodes using **TLS** |

### 💡 Redis/Valkey vs. Memcached — worth knowing which is which

| | **Redis / Valkey** | **Memcached** |
|---|---|---|
| Data structures | Rich: lists, sets, **sorted sets**, hashes | Simple key-value strings only |
| Replication and failover | **Yes** | No |
| Persistence / snapshots | **Yes** | No |
| Multi-AZ | **Yes** | No |
| Pick it for | Leaderboards, session stores, pub/sub, anything needing durability or HA | A dead-simple, purely ephemeral cache you can scale horizontally |

*(**Valkey** is the open-source fork of Redis, and now AWS's recommended default — which is
why your notes list three engines where older courseware lists two.)*

💡 **Why leaderboards are the classic Redis example:** a **sorted set** keeps millions of
scores permanently ranked, so "top 10 players" and "what rank am I?" are instant. In SQL that
means an `ORDER BY` over millions of rows on every single request.

### 🧒 ELI5 — the snack bowl

The kitchen is downstairs (**the database**). Every time you want a biscuit you could walk
down, open the cupboard, walk back up — 30 seconds a biscuit.

Instead you put a **bowl of biscuits on your desk** (**the cache**). Now a biscuit takes half
a second. You still go downstairs occasionally to refill the bowl, but 99 times out of 100 the
bowl has what you want.

Two things to remember about the bowl: it's **small**, so only the popular snacks live there —
and it's **not where food really lives**. Knock the bowl over and no food is lost; you just
refill it from the kitchen. **A cache is a copy, never the original.**

### 🏢 Real example

A news site's homepage runs the same "top 10 stories" query for every visitor. At 50,000
visitors an hour that's 50,000 identical database queries. With ElastiCache the result is
cached for 60 seconds: the database handles **60 queries an hour** instead of 50,000, page
loads drop from 800 ms to 40 ms, and the site survives a traffic spike that would have
flattened the database.

## 8. Amazon DocumentDB

**Amazon DocumentDB (with MongoDB compatibility)** is a fully managed service designed to
handle **semistructured data** — information that **doesn't conform to rigid relational
schemas**. Being **MongoDB-compatible**, it manages **JSON-like documents with dynamic
schemas**.

It's **perfect for applications requiring frequent schema changes and document-oriented
data**. Unlike relational or other nonrelational databases, **you can iterate quickly without
relying on predefined schemas**. It can **store, query, and index JSON data effortlessly**,
with **automatic scaling, continuous backup, and enterprise-grade security**.

### Use cases

**Content management systems**, **catalog and inventory management**, and **user profile and
personalization systems**.

### Benefits

| Benefit | What it means |
|---|---|
| **MongoDB compatibility** | Fully compatible with MongoDB workloads — supports MongoDB **APIs, drivers, and tools**. **Existing MongoDB code and skills work without modification**, and applications migrate with **minimal code changes** |
| **Performance and scalability** | Storage **scales automatically up to 64 TB in 10 GB increments**. Handles **millions of requests per second** with consistent performance. Compute scales **up or down** as needed |
| **Increased read throughput** | Up to **15 replica instances that share the same underlying storage**, improving read throughput for high-volume applications |

### 📌 DynamoDB vs. DocumentDB — both NoSQL, very different

| | **DynamoDB** | **DocumentDB** |
|---|---|---|
| Model | **Key-value** (and document) | **Document** (JSON) |
| Compatible with | AWS's own API | **MongoDB** APIs, drivers, tools |
| Instances to manage | **None** — fully serverless | You choose instance sizes |
| Querying | Key lookups; limited querying of attributes | **Rich document queries** and indexing on any field |
| Pick it when | You need extreme scale and predictable single-digit-ms latency | You **already use MongoDB**, or need to query *inside* documents flexibly |

💡 **Exam signal:** the word **MongoDB** in a question means **DocumentDB**, essentially every
time.

### 🧒 ELI5 — the scrapbook

DynamoDB was a locker room: say a name, get the whole locker, done.

**DocumentDB is a shelf of scrapbooks.** Each scrapbook (**a document**) is about one thing —
one product, one user — and inside, the pages can be laid out however that thing needs. One
product's scrapbook has three photos and a size chart; another has a video and no photos.

The difference from the locker: **you can flip through and search inside the scrapbooks.**
*"Find every scrapbook that mentions a red hat on page 2"* — that works here, and it's exactly
what the locker room couldn't do.

## 9. Amazon Neptune

**Neptune** is a **fully managed, purpose-built graph database** that manages **highly
connected data sets**, like those in social networking applications. It **excels at
understanding complex relationships that are difficult to identify in traditional relational
databases** — user connections, friend networks, interaction patterns. It **maintains high
performance even as data complexity grows**, and offers **high availability with automatic
failover and backups**.

### Use cases

**Social network user connection mapping**, **fraud detection systems**, and **search and
recommendation systems**.

### Benefits

| Benefit | What it means |
|---|---|
| **Purpose-built for complex relationships** | Stores and queries **highly connected data using graph models**. Supports both **property graph** and **Resource Description Framework (RDF)** models — ideal for **relationship mapping and pattern matching** |
| **High performance and scalability** | **Processes billions of relationships in milliseconds**, with consistent performance at scale. Storage **grows automatically up to 64 TB**. A purpose-built engine optimizes graph queries for **fast traversal of connected data points** |

### 💡 Why relationships break relational databases

"Find friends-of-friends-of-friends of this user" in SQL means **three self-joins** over a
huge table. Add a fourth hop and the query time explodes. A graph database **stores the
connection itself as a first-class thing**, so traversing a hop is a pointer follow, not a
search. Six hops costs barely more than one.

### 🧒 ELI5 — the pin-and-yarn board

A relational database is a list of names. A graph database is a **corkboard with pins and
yarn**: each pin is a person, and each piece of yarn is a friendship.

Now ask: *"who are my friends' friends' friends?"* With the **list**, you read the whole list
of names, then read it again for each friend, then again for each of theirs — thousands of
passes. With the **corkboard**, you just **follow the yarn** with your finger. Three hops takes
three seconds no matter how big the board is.

That's why banks use it to catch fraud: *"is this new account connected, through any chain of
shared phone numbers, addresses, or devices, to an account we already banned?"* is a yarn
question, not a list question.

### 🏢 Real example

A bank's fraud team gets a new loan application. Neptune traverses: this applicant → shares a
phone number with → an account that shares a device with → an account that shares a bank
account with → **three accounts flagged for fraud last year**. Four hops, answered in
milliseconds, on a graph with billions of edges. In SQL, that query would be a nightly batch
job.

## 10. AWS Backup

**AWS Backup** streamlines data protection across **various AWS resources and on-premises
deployments** by providing a **single dashboard** for monitoring and managing backups. It
**eliminates the complexity of managing multiple backup strategies** by supporting multiple
storage types, including **EBS volumes**, **EFS file systems**, and **various databases**.

It **centralizes and automates data protection**, improving consistency and reducing
administrative overhead, and offers **flexible scheduling**, **encryption**, and
**cross-Region backup support** for enhanced disaster recovery.

### Use cases

**Centralized disaster recovery**, **consistent backup policies for compliance requirements**,
and **consolidating multiple backup processes through a single interface**.

### Benefits

| Benefit | What it means |
|---|---|
| **Centralized backup management** | A **single dashboard** across **multiple AWS services and accounts**. Monitor backup jobs, restore points, and **verify compliance status** in one place, reducing operational complexity and configuration errors. Create **automated schedules** aligned to business and compliance needs, with policies that **automatically protect new resources as they're created** |
| **Cross-Region backup redundancy** | **Automatic replication of backup data across Regions** for disaster recovery. Restore from a **secondary Region** if the primary has an outage — meeting compliance requirements while guaranteeing accessibility during Regional failures |
| **Streamlined regulatory compliance** | Maintains **detailed audit logs and reports** to demonstrate compliance. **Enforce backup policies across your organization** and **track backup activities** for security and compliance |

💡 **How this connects to `Storage.md`:** there you learned **EBS snapshots** and **Data
Lifecycle Manager**, which back up *EBS only*. **AWS Backup is the tier above** — one policy,
one dashboard, one audit trail covering EBS, EFS, RDS, DynamoDB, DocumentDB, Neptune, FSx, S3,
and on-premises resources via Storage Gateway. The value isn't new capability, it's **not
having eight separate backup systems to prove compliance against**.

⚠️ That "automatically protect new resources as they're created" line is the quietly important
one: the most common real backup failure is not a broken backup, it's a resource **nobody
added to the backup plan**.

### 🧒 ELI5 — one homework folder

You have homework in your school bag, in your desk, on the computer, and in your locker. Every
night you have to remember to check **four different places**. Eventually you forget one, and
that's the one the teacher asks for.

AWS Backup is **one folder with one checklist**, and it checks **all four places for you** —
every night, automatically. If a new place appears (you get a second locker), it gets added to
the list without you noticing. And it keeps a **receipt for every check**, so when the teacher
asks "did you do it?" you can prove it.

## 11. Choosing the right database

### The decision flow

```
 What shape is your data?
 │
 ├── ROWS AND COLUMNS, with relationships and SQL queries
 │   │
 │   ├── Need Oracle, SQL Server, MariaDB, or lowest cost? ──► Amazon RDS
 │   └── MySQL/PostgreSQL-compatible, want max performance,
 │       availability, and auto-scaling? ────────────────────► Amazon Aurora
 │
 ├── ITEMS WITH A UNIQUE KEY, flexible attributes,
 │   massive scale, single-digit-ms latency ─────────────────► Amazon DynamoDB
 │
 ├── JSON DOCUMENTS with changing structure
 │   (especially if you already use MongoDB) ────────────────► Amazon DocumentDB
 │
 ├── RELATIONSHIPS are the thing you query
 │   (social graphs, fraud rings, recommendations) ──────────► Amazon Neptune
 │
 └── A COPY of hot data you read constantly
     (sessions, query results, leaderboards) ────────────────► Amazon ElastiCache

 And regardless of which you chose:
     one dashboard and one policy for backing it all up ─────► AWS Backup
```

## 12. Quick recap + common exam traps

### Recap

- **Relational** = fixed schema, rows and columns, SQL, relationships between tables.
  **NoSQL** = items with unique keys and **flexible attributes you can change anytime**.
- **RDS** is managed relational across **six engines** (Aurora, MySQL, PostgreSQL, SQL Server,
  MariaDB, Oracle). It handles **backups, patching, and hardware provisioning**.
- **Multi-AZ** = availability (synchronous standby, automatic failover, not readable).
  **Read replicas** = performance (asynchronous, readable).
- **Aurora** = MySQL/PostgreSQL-compatible with AWS's own storage engine: **6 copies across
  3 AZs**, **up to 15 read replicas**, storage auto-growing to **128 TiB**, up to **5× MySQL**
  throughput.
- **DynamoDB** = serverless key-value NoSQL, **single-digit millisecond** at any scale,
  **99.999% availability** across **three facilities per Region**, no instances to manage.
- **In-memory caches** live in **RAM** — hundreds to thousands of times faster than disk. The
  app **checks the cache first**, reducing load on the primary database.
- **ElastiCache** = managed **Redis / Valkey / Memcached**, with automatic failed-node
  replacement and multi-AZ replication.
- **DocumentDB** = managed **MongoDB-compatible** document database, 64 TB, 15 replicas.
- **Neptune** = **graph** database for highly connected data; property graph and RDF; billions
  of relationships in milliseconds.
- **AWS Backup** = one dashboard, one policy set, cross-Region redundancy, audit logs — across
  services, accounts, and on-premises.

### Traps

| Trap | The truth |
|---|---|
| "RDS supports MongoDB" | **No.** RDS's six engines are Aurora, MySQL, PostgreSQL, SQL Server, MariaDB, Oracle. MongoDB-compatible = **DocumentDB** |
| "DynamoDB is a relational database because it has tables" | It has tables, but **no fixed schema and no joins**. It's **NoSQL key-value** |
| "A Multi-AZ standby can serve read traffic" | **No** — it sits idle until failover. Readable copies are **read replicas** |
| "Read replicas give you automatic failover" | **No** — that's Multi-AZ. Promoting a read replica is a manual action |
| "Aurora is just RDS running MySQL" | It's MySQL/PostgreSQL-*compatible* with a **completely different storage engine** — 6 copies, 3 AZs, auto-scaling storage |
| "A cache is where the data lives" | A cache is a **temporary copy**. Lose it and you lose nothing — you refill it from the database |
| "Use ElastiCache as your primary database" | It's a **caching layer** in front of a real database, not a replacement for one |
| "DynamoDB replicates across Regions automatically" | Within a Region, across **three facilities**, yes. **Cross-Region requires Global Tables**, which you enable |
| "Neptune is for any large dataset" | It's for data where the **relationships are the query**. Big-but-simple data is better off in DynamoDB or RDS |
| "AWS Backup replaces EBS snapshots and DLM" | It **orchestrates** them (and much more) from one place. The underlying snapshot mechanisms are the same |
| "Redis and Memcached are interchangeable" | Only **Redis/Valkey** offer replication, failover, persistence, multi-AZ, and sorted sets |
