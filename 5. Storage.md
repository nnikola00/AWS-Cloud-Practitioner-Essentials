## 1. The three storage types

Everything in this module hangs off one distinction. Get this and the services sort
themselves out.

| | **Block storage** | **Object storage** | **File storage** |
|---|---|---|---|
| **Data is…** | Raw blocks on a volume | Whole objects in a flat namespace | Files in a folder hierarchy |
| **To change 1 byte** | Rewrite just that **block** | Rewrite the **entire object** | Rewrite just that part of the file |
| **Attached to** | **One** EC2 instance at a time | Nothing — accessed over HTTP APIs | **Many** instances at once |
| **Structure** | None (the OS puts a file system on it) | **Flat** address space + metadata | Hierarchical directory tree |
| **Accessed by** | The OS, as a disk | API / SDK / URL | Network protocols (NFS, SMB) |
| **AWS services** | **Instance store**, **EBS** | **S3** | **EFS**, **FSx** |
| **Best for** | Boot volumes, databases, low-latency workloads | Backups, media, data lakes, static websites | Shared content, home directories, lift-and-shift apps |

### 🧒 ELI5 — three ways to keep your stuff

- **Block storage is your own desk drawer.** It's bolted to *your* desk, only you can reach
  it, and it's the fastest thing to grab from. You can rearrange one small thing inside
  without touching everything else. But if you move to a different desk, the drawer doesn't
  come with you unless you unbolt it and carry it over.
- **Object storage is the coat check at a museum.** You hand over your whole coat and get a
  numbered ticket (**the key**). You can't reach into the coat while it's back there and swap
  one button — to change anything you hand in the whole coat again. But they'll take an
  unlimited number of coats, from anyone, from anywhere in the world, and never lose one.
- **File storage is the shared filing cabinet in the middle of the office.** It has drawers
  inside drawers (**folders**), everyone can open it at the same time, and two people can
  work out of the same folder at once.

**📌 The single most useful test:** *how many machines need to read and write this at the
same time?* **One → block (EBS).** **Many → file (EFS/FSx).** **None, it's accessed over the
web → object (S3).**

### The five services in the module, plus two extras

| Service | Type | One-line identity |
|---|---|---|
| **EC2 instance store** | Block | **Unmanaged, non-persistent**, physically attached to the host — temporary data only |
| **Amazon EBS** | Block | **Managed, persistent** volumes for EC2 — various types for various workloads |
| **Amazon S3** | Object | Fully managed, scalable object storage for any amount of data, from anywhere |
| **Amazon EFS** | File | Fully managed, scalable **NFS** file system for AWS and on-premises |
| **Amazon FSx** | File | Fully managed **third-party** file systems: Windows, Lustre, NetApp ONTAP, OpenZFS |
| **AWS Storage Gateway** | Hybrid | Gives on-premises systems access to virtually unlimited cloud storage |
| **AWS Elastic Disaster Recovery** | Hybrid/DR | Streamlines recovery of physical, virtual, and cloud servers into AWS |

## 2. Amazon EC2 instance store — temporary block storage

**📌 Instance store is not a standalone AWS service.** It refers to **block-level storage
physically attached to the host computer** your EC2 instance runs on. Depending on the
instance type, it may come attached as the default storage.

**Because its data is lost when the instance is stopped or terminated**, instance store suits
**temporary** needs: buffers, caches, and scratch data. **It is not recommended for
applications that require data retention.**

### Key takeaway: no data persistence

> Instance store provides **temporary** block-level storage. **If you stop or terminate the
> instance, all data written to the attached instance store is deleted.**

### ⬛ Filled gap — what happens to instance store data on each action

Your notes have "choose each of the following three numbered markers" with nothing under it.
Here's what it covers:

| Action | What happens to instance store data |
|---|---|
| **Reboot** | **Data survives.** A reboot keeps the instance on the same physical host. |
| **Stop** | **Data is lost.** Stopping releases the host; restarting lands you on a *different* physical machine, with different (empty) local disks. |
| **Terminate** | **Data is lost**, permanently. |
| **Host failure** | **Data is lost.** There is no redundancy — it's one set of physical disks. |

💡 **Why this is the way it is:** instance store *is* the actual SSD/NVMe inside the server
rack. Its speed comes from being physically bolted to the machine — and that's exactly why
the data can't follow you to a different machine. **The speed and the impermanence are the
same fact.**

### Benefits

| Benefit | What it means |
|---|---|
| **Automatically available storage** | ⬛ On instance types that include it, the disks are already there on launch — nothing to create, attach, or pay for separately |
| **Cost effective** | ⬛ The cost is bundled into the instance price. No separate per-GB storage charge |
| **High performance** | Extremely low-latency storage **directly attached to the host server**. That proximity means exceptionally high I/O performance — ideal for temporary storage of data needing fast processing |

### 🧒 ELI5 — the whiteboard in a hotel room

Your hotel room has a whiteboard on the wall. It's right there, it's free with the room, and
scribbling on it is instant — much faster than walking to the business centre.

But when you **check out** (stop/terminate the instance), the cleaners wipe it. And even if
you book the same hotel again tomorrow, you'll get a **different room with a different
whiteboard**. Step out for lunch and come back to the same room (a **reboot**) and your notes
are still there.

So: brilliant for working notes. Terrible for your passport.

### 🏢 Real example

A video transcoding service downloads a 4 GB source file, decodes it into hundreds of
gigabytes of intermediate frames, re-encodes it, and uploads the finished MP4 to S3. Those
intermediate frames are written to **instance store** — they need to be fast, they're
recreatable, and nobody cares if they vanish. The **output** goes to S3, because that has to
survive.

## 3. Amazon EBS — persistent block storage

**Amazon Elastic Block Store (EBS)** provides **persistent** block-level storage volumes for
EC2 instances. EBS volumes **act like external hard drives**, offering consistent, low-latency
performance for workloads like databases and file systems.

**How you use one:** define the configuration (volume **size** and **type**), create the
volume, then **attach** it to an EC2 instance. Because EBS holds data that needs to persist,
**backing it up matters** — the recommendation is **incremental backups via EBS snapshots**.

EBS volumes can be **backed up, resized, and attached to different EC2 instances**, and
**modified while in use** without disrupting the instance.

### Key takeaway: data persistence

> **If you stop or terminate an EC2 instance, all the data on the attached EBS volume remains
> available.**

### ⬛ Filled gap — what happens to EBS data on each action

The counterpart to the instance store table above:

| Action | What happens to the EBS volume |
|---|---|
| **Reboot** | Volume and data are untouched |
| **Stop** | **Data persists.** The volume stays attached, waiting. You still pay for the storage, but not for the stopped instance's compute |
| **Terminate** | Depends on the volume's **`DeleteOnTermination`** flag. The **root** volume defaults to **true** (deleted); volumes you attach yourself default to **false** (kept) |
| **Detach and reattach elsewhere** | Data comes with the volume — this is the portability benefit below |

💡 **This is the single most tested contrast in the storage module:**
**instance store = ephemeral. EBS = persistent.**

### ⚠️ The constraint the notes don't mention

**An EBS volume lives in one Availability Zone and can only attach to an instance in that
same AZ.** It's not a Region-wide resource. If your instance is in `us-east-1a`, its volume
must be too.

To move data to another AZ you **take a snapshot** (snapshots *are* Region-wide) and create a
new volume from it there. This is why snapshots matter beyond just backup.

### Use cases

Database hosting, backup storage for applications, and rapid deployment of development
environments using volume snapshots.

### Benefits — portability (detach and reattach)

EBS volumes support **data portability**: you can detach a volume from one instance and
attach it to another. Your notes list five reasons with no detail — here's what each means:

| Reason | ⬛ What it actually means |
|---|---|
| **Data migration** | Move a dataset to a new instance without copying it over the network — just move the disk |
| **Instance type changes** | Right-sizing from `t3.medium` to `r6i.large`? Stop the instance, detach the data volume, attach it to the new one. The data never moves |
| **Disaster recovery** | If an instance fails but the volume is healthy, attach it to a replacement instance and you're back |
| **Cost optimization** | Detach a volume from a running instance and keep just the volume — you stop paying for compute while retaining the data |
| **Performance tuning** | Swap a volume onto an instance with more network/EBS bandwidth, or change the volume type (e.g. `gp3` → `io2`) without rebuilding anything |

### 🧒 ELI5 — the external hard drive

Instance store was the whiteboard in the hotel room. **EBS is a USB hard drive you brought
with you.**

Turn the laptop off (**stop the instance**) and the drive still has everything on it. Buy a
new laptop (**change instance type**) and you just unplug the drive and plug it into the new
one — all your files are there.

Two rules, though: **only one laptop can have it plugged in at a time**, and **you have to be
in the same room as the drive** (the same Availability Zone) to plug it in.

### 💡 EBS volume types (beyond the course, but it makes "various types" concrete)

| Type | Backed by | Built for |
|---|---|---|
| **gp3** / gp2 | SSD | **General purpose** — boot volumes, most workloads. `gp3` is the current default |
| **io2 Block Express** / io1 | SSD | **Provisioned IOPS** — the most demanding databases (SAP HANA, Oracle, high-transaction SQL) |
| **st1** | HDD | **Throughput optimized** — big sequential reads: log processing, data warehouses |
| **sc1** | HDD | **Cold** — lowest cost, infrequently accessed data |

Rule of thumb: **SSD for lots of small random operations (IOPS), HDD for large sequential
streaming (throughput).**

## 4. EBS snapshots — the data lifecycle

### What a snapshot is

**EBS snapshots are point-in-time backups of an EBS volume.** Uses: disaster recovery, data
migration, volume resizing, and consistent backups of production workloads.

**Snapshots are incremental** — they save only the blocks that have **changed since your most
recent snapshot**.

Snapshots can create **multiple new volumes**, and a new volume created from a snapshot is an
**exact copy** of the original at the moment the snapshot was taken. **Snapshots are stored
redundantly across multiple Availability Zones using Amazon S3.**

### How the incremental chain works

```
  Volume:  [A][B][C][D]        ← 4 blocks of data

  Day 1 ── SNAPSHOT 1 (initial): FULL copy
           stores → A B C D                        (4 blocks stored)

  Day 2 ── you change block C to C'
           SNAPSHOT 2 (incremental)
           stores → C'         + references A B D  (1 block stored)

  Day 3 ── you change block A to A'
           SNAPSHOT 3 (incremental)
           stores → A'         + references B C' D (1 block stored)

  Total stored: 6 blocks — not 12.
  But EACH snapshot still restores a COMPLETE volume.
```

**The three stages, as your course lays them out:**

1. **Initial snapshot** — the first snapshot of a volume is a **full copy** of all data in use
   at that point in time. It's the **baseline** containing every in-use block.
2. **Subsequent incremental snapshots** — only **changed blocks since the last snapshot** are
   captured. Much **smaller and faster** to create. Each one holds **references to previous
   snapshots**, forming a chain that enables point-in-time recovery.
3. **Snapshot consolidation and management** — despite being incremental, **each snapshot
   appears as a full point-in-time copy** of the volume. AWS manages the relationships
   between snapshots **automatically**. **When you delete a snapshot, only data unique to it
   is removed** — data referenced by other snapshots is preserved.

### 🧒 ELI5 — photos of your bedroom

**Monday:** you take a full photo of your whole bedroom. Everything is in it.

**Tuesday:** you moved one toy. Instead of photographing the entire room again, you photograph
**just the shelf that changed** and write "everything else: see Monday's photo."

**Wednesday:** you photograph only the desk. "Rest: see Tuesday."

Here's the clever part: **when you look at Wednesday's photo, you see the whole room** — the
system quietly fetches the unchanged bits from the earlier photos. And if you throw away
Tuesday's photo, it only bins the shelf picture, because Monday's and Wednesday's photos still
need everything else.

You get a complete picture of every single day, while storing almost nothing extra.

### ⚠️ Working with snapshots — your responsibility

Per the **AWS Shared Responsibility Model**, **you** are responsible for:

- **Scheduling and managing regular snapshots** as part of your backup strategy
- **Monitoring snapshot costs** and **deleting unnecessary snapshots** to avoid excessive charges
- Making sure **sensitive data within snapshots is encrypted**
- **Verifying snapshot integrity** and **testing restoration procedures regularly**

💡 **"A backup you have never restored is not a backup."** The exam likes this framing: AWS
provides the *capability*; the *strategy* is yours.

### Benefits of snapshots

| Benefit | ⬛ What it means |
|---|---|
| **Data protection and recovery** | A recoverable point-in-time copy stored redundantly across multiple AZs — so an AZ failure, an accidental deletion, or a corrupted volume doesn't mean data loss |
| **Operational flexibility** | One snapshot can spawn **many** volumes: clone production into a test environment, resize a volume, or move data to another AZ or Region |
| **Cost effective** | Incremental storage means you pay roughly for **changed blocks only**, not a full copy per backup |

### Amazon Data Lifecycle Manager (DLM)

**Automates the creation, retention, and deletion of EBS snapshots.** It can **schedule
snapshots during off-peak hours** to minimize performance impact and **automatically delete
outdated backups** to control storage costs. Especially valuable for large-scale deployments
where manual snapshot management would be time-consuming and error-prone.

**Creating a custom policy — the five steps:**

| Step | What you do |
|---|---|
| **1. Create an EBS snapshots policy** | Via the EC2 console, API calls, the AWS CLI, SDKs, or **AWS CloudFormation** |
| **2. Select target resource type** | Choose an **EBS volume** or an **EC2 instance** as the snapshot target |
| **3. Exclude volumes** | Narrow what's included by excluding either the **root volume** or the **data volumes** |
| **4. Set custom schedules** | Automate creation, retention, and deletion on your own schedule |
| **5. Apply additional actions** | Configure tags, **snapshot archiving**, **EBS fast snapshot restore**, **cross-Region copying**, and **cross-account sharing** |

**🧒 ELI5:** DLM is the **automatic camera on a timer**. Instead of remembering to photograph
your room every night, you set it once: *"photo every night at 2 a.m., keep the last 30, bin
anything older."* It never forgets, and it never fills the album with junk.

## 5. Amazon S3 — object storage

**Amazon Simple Storage Service (S3)** is a **fully managed, highly available object storage
service** for storing and retrieving **any amount of data as objects**. It offers
**99.999999999% durability** — your data is highly protected against loss — plus
**versioning**, **lifecycle management**, and **various storage classes** to optimize costs.

S3 stores files as **objects** inside containers called **buckets**. Each object can range
from **a few bytes to several terabytes**. It integrates with other AWS services and supports
use cases from basic backups to complex **data lakes**.

### 💡 What "eleven nines" actually means

**99.999999999%** durability = if you store **10,000,000 objects**, you can expect to lose
**one object every 10,000 years**. AWS achieves it by automatically storing every object
redundantly across **multiple facilities (AZs)** within your chosen Region.

**📌 Durability ≠ availability.** *Durability* is "will my data still exist?" (eleven nines).
*Availability* is "can I reach it right now?" (99.99% for S3 Standard). The exam sometimes
swaps these.

### Elements

#### S3 objects

An **object** is the **fundamental unit of data storage**. Upload a file and it becomes an
object, **stored durably across multiple facilities within your chosen Region**.

Each object typically includes:

| Part | What it is |
|---|---|
| **The data** | The file contents itself — any type: images, videos, documents, application data |
| **Metadata** | System and **user-defined** information about the object |
| **Key** | The **unique identifier** within the bucket — essentially its file name |

Objects also have properties like **version ID**, **access control information**, and
**user-defined metadata**. Size range: a few bytes to several terabytes.

#### S3 buckets

A **bucket** is a **container for objects**. Key facts:

- Bucket names are **globally unique across all of AWS** — not just your account, *everyone's*.
- Buckets are the **basic unit for access control** and hold a **virtually unlimited** number
  of objects.
- They let you **group related objects** and **apply policies at the bucket level**.
- When creating one you specify its **name** and **Region**. Configurable settings include
  **versioning**, **logging**, and **access permissions**.

### 📌 The "flat namespace" point people get wrong

S3 has **no real folders.** The console *shows* folders, but a key like
`2026/invoices/march.pdf` is just **one long string** — the slashes are characters, not
directory structure. That's what "flat address space" means.

It matters because renaming a "folder" isn't a rename — it's copying every object to a new key
and deleting the old ones.

### 🧒 ELI5 — the world's biggest coat check

Imagine a coat check with **infinite** space.

- You hand over a coat (**an object**) and they write a **ticket number** on it (**the key**).
- Your coats go on **your own rack** (**the bucket**), and no two racks in the *entire world*
  can share a name — that's why `my-bucket` is always taken and you end up with
  `nikola-aws-notes-2026`.
- You can't reach in and sew a button on a coat that's already checked. To change it, you
  hand in a whole new coat with the same ticket number.
- They keep **eleven copies in eleven different buildings**, so a fire in one loses nothing.
- Anyone with your ticket number *and your permission* can pick it up — from anywhere in the
  world, over the internet.

### Benefits

| Benefit | ⬛ What it means |
|---|---|
| **Virtually unlimited storage** | No capacity to provision. No volumes to resize. One object or a hundred billion — same service, same API |
| **Object lifecycle management** | Rules automatically move objects to cheaper classes or delete them as they age (see §6) |
| **Broad range of use cases** | Backup and archive, static website hosting, data lakes and analytics, media distribution (the origin behind CloudFront), software distribution, log storage |

### Security and privacy management

> **Everything you store in S3 is private by default. You must explicitly grant permissions
> to access these resources.**

If you *want* data available to everyone on the internet, you **can** choose to make buckets
and objects public. For more granular control, S3 provides three mechanisms:

| Feature | What it is |
|---|---|
| **Bucket policies** | **Resource-based** policies attached **only to S3 buckets**. Specify which actions are **allowed or denied** on the bucket **and every object in it** |
| **Identity-based policies** | Permissions controlling what **users, groups, or roles** can do with S3 resources. Attached to the **identity**, not the resource. Specify which buckets and objects a user can access and which actions they can perform |
| **Encryption** | **At rest** — secures stored objects against unauthorized access. **In transit** — safeguards data traveling to and from S3, maintaining secure client-service communication |

**🧒 ELI5 of the two policy types:** a **bucket policy** is a sign on the **door of the room**
listing who may enter. An **identity-based policy** is what's written on **your own ID badge**
listing which rooms you may enter. Both get checked — the sign on the door *and* your badge.

⚠️ **Public S3 buckets are one of the most common real-world cloud data breaches.** The
default is private for a reason; making a bucket public should be a deliberate decision (a
static website), never a shortcut to fix a permissions error.

## 6. S3 storage classes and S3 Lifecycle

S3 offers multiple **storage classes** for workloads with different **performance, access,
resiliency, and cost** requirements. They also address **data residency** requirements,
**unpredictable access patterns**, and **archival** needs.

### The nine storage classes

| Class | AZs | Retrieval time | Use it for |
|---|---|---|---|
| **S3 Standard** | ≥3 | Milliseconds | **General purpose / the default.** Cloud applications, dynamic websites, content distribution, mobile and gaming apps, big data analytics. *An object uploaded without a specified class goes here.* |
| **S3 Intelligent-Tiering** | ≥3 | Milliseconds | **Unknown or changing access patterns.** Stores objects across a **frequent access** tier, an **infrequent access** tier, and an **archive instant access** tier, and **monitors access patterns to move data automatically** to the most cost-effective tier |
| **S3 Standard-IA** | ≥3 | Milliseconds | Data **accessed less frequently but needing rapid access**. Same durability, throughput, and latency as Standard, with a **lower per-GiB storage price** but a **per-GiB retrieval fee**. Long-term backups, disaster recovery files |
| **S3 One Zone-IA** | **1** | Milliseconds | Infrequently accessed data **without high availability needs**. Cheaper than Standard-IA (which uses three zones). **Secondary backups or easily recreatable data** |
| **S3 Express One Zone** | **1** | **Single-digit ms** | Your **most frequently accessed** data and **latency-sensitive** applications. Up to **10× faster** access and **80% lower request costs** than S3 Standard |
| **S3 Glacier Instant Retrieval** | ≥3 | **Milliseconds** | Archiving data that's **rarely accessed but needs millisecond retrieval**. Up to **68% cheaper** than Standard-IA at the same latency and throughput |
| **S3 Glacier Flexible Retrieval** | ≥3 | **1–5 min** (expedited) or **5–12 h** (bulk, free) | Archived data accessed **1–2 times per year**. Backup, disaster recovery, offsite storage — when some data occasionally must come back in minutes |
| **S3 Glacier Deep Archive** | ≥3 | **12 hours** (default) | **The lowest-cost class.** Long-term retention and digital preservation, accessed maybe once or twice a year. Designed for **7–10+ year** retention for **regulatory compliance** — financial services, healthcare, public sector |
| **S3 on Outposts** | On-prem | Local | Object storage **in your own AWS Outposts environment** via S3 APIs, for **local data residency** requirements and keeping data close to on-premises applications |

### 💡 The pattern behind the list

There are really only **three questions**, and every class is an answer to some combination:

```
  1. HOW OFTEN do you read it?
        often ─────────────► Standard  (or Express One Zone if latency-critical)
        rarely ────────────► Standard-IA
        almost never ──────► a Glacier class

  2. HOW FAST must it come back?
        milliseconds ──────► Glacier Instant Retrieval
        minutes ───────────► Glacier Flexible Retrieval
        hours are fine ────► Glacier Deep Archive   (cheapest)

  3. Can you afford to LOSE it if one AZ burns down?
        no ────────────────► any 3-AZ class
        yes, it's a copy ──► One Zone-IA  (cheaper)

  Don't know the answers? ──► Intelligent-Tiering decides for you.
```

**The trade-off is always the same:** cheaper storage ⇄ slower retrieval and/or a retrieval
fee. Nothing is free — a class that's cheap to *store* charges you to *read*.

### 🧒 ELI5 — where you keep your toys

- **S3 Standard** — toys **on the floor**, played with daily. Grab them instantly.
- **Express One Zone** — the toy **in your hand**. Absolute fastest, but only in this one room.
- **Standard-IA** — the box **on the shelf in your closet**. Cheaper to keep there. You can
  get it in a second, but Mum charges you 10 cents each time she reaches it down.
- **One Zone-IA** — the same closet box, but **only in one house**. Cheapest shelf, and if
  that house floods the box is gone. Fine, because it's a *spare* set of toys.
- **Glacier Instant Retrieval** — the **attic with a drop-down ladder**. Cheap to store, and
  still quick to grab.
- **Glacier Flexible Retrieval** — the **storage unit across town**. Very cheap. Someone has
  to drive over: a few minutes if you pay for the fast trip, half a day if you wait for the
  free one.
- **Glacier Deep Archive** — the **box buried in your grandparents' basement in another
  country**. Almost free to leave there. If you want it, ask today and it arrives tomorrow.
- **Intelligent-Tiering** — a **robot butler** who watches which toys you actually play with
  and quietly moves them between the floor, the closet, and the attic so you're never paying
  for floor space you don't use.

### S3 Lifecycle

To avoid **manually** managing storage tiers, use **S3 Lifecycle configurations** to automate
it. A lifecycle configuration on an object or group of objects automates **two kinds of
action**:

| Action type | What it does |
|---|---|
| **Transition actions** | Define **when objects move to another storage class** |
| **Expiration actions** | Define **when objects expire and are permanently deleted** |

**Examples from the course:** transition objects to **S3 Standard-IA 30 days** after
creation; archive objects to **S3 Glacier Deep Archive 1 year** after creation.

**A lifecycle policy in plain English:**

```
  Day 0    ─ object created ──────────► S3 Standard
  Day 30   ─ transition ─────────────► S3 Standard-IA
  Day 90   ─ transition ─────────────► S3 Glacier Flexible Retrieval
  Day 365  ─ transition ─────────────► S3 Glacier Deep Archive
  Day 2555 ─ expiration ─────────────► deleted  (7 years — compliance satisfied)
```

You write that rule **once**. Every object that ever lands in the bucket follows it
automatically, forever.

### Lifecycle use cases

| Situation | The rule |
|---|---|
| **Periodic logs** | You upload logs your application needs for a week or a month — **then delete them** (an expiration action) |
| **Data that changes in access frequency** | Documents accessed frequently for a limited period, then infrequently, then not needed in real time at all — but your organization or **regulations require archiving** for a set period, after which you can delete |

**🏢 Real example:** a company generates 50 GB of application logs daily. Engineers query
yesterday's logs constantly and last month's occasionally; auditors require 7 years of
retention. One lifecycle policy (the ladder above) handles all of it — and cuts the storage
bill by roughly 95% versus leaving everything in Standard, with zero ongoing effort.

## 7. Amazon EFS — shared file storage

**Amazon Elastic File System (EFS)** is a **fully managed, scalable file storage service** for
AWS cloud services **and on-premises resources**. It uses the **Linux Network File System
(NFS)** protocol and **automatically scales to petabytes** as you add or remove files
**without disrupting applications**. It supports a wide variety of workloads and can be
**accessed by multiple EC2 instances simultaneously**.

### Benefits

| Benefit | ⬛ What it means |
|---|---|
| **Multi-AZ redundancy** | Data is stored **across multiple Availability Zones**, so an AZ failure doesn't take your file system down — and instances in **any** AZ in the Region can mount it |
| **Shared access** | **Many** EC2 instances (and containers, and Lambda functions) read and write the **same files at the same time** — the thing EBS cannot do |
| **Elastic storage** | Grows and shrinks **automatically** as you add and remove files. **No provisioning, no resizing**, and you pay only for what you use |

### 📌 EBS vs. EFS — the comparison the exam wants

| | **Amazon EBS** | **Amazon EFS** |
|---|---|---|
| Storage type | **Block** | **File** |
| Attached to | **One** instance at a time | **Many** instances simultaneously |
| Scope | **One Availability Zone** | **Regional** — spans multiple AZs |
| Capacity | **You provision** a size (and resize it) | **Automatic**, to petabytes |
| Protocol | Presented as a raw disk to the OS | **NFS** over the network |
| Pay for | The **provisioned** size | The storage **actually used** |
| Typical use | Boot volume, single-instance database | Shared content, home directories, CMS media, shared config |

### 🧒 ELI5 — the family fridge

**EBS is a lunchbox.** It's yours, you carry it, and nobody else can open it while you have it.

**EFS is the fridge in the kitchen.** Everyone in the house opens it at the same time, takes
things out, and puts things in. When you buy more groceries, the fridge just… gets bigger
(magic fridge). And there's a **second identical fridge in the neighbour's house
automatically kept in sync**, so if your kitchen floods, dinner still happens.

### 🏢 Real example

A WordPress site runs on 6 EC2 instances behind a load balancer. When an editor uploads an
image, **every** instance must be able to serve it — otherwise the image 404s for 5 out of 6
visitors. EBS can't do this (one volume, one instance). **EFS can:** all 6 instances mount the
same file system at `/var/www/html/wp-content/uploads`, and the upload is instantly visible to
all of them.

### EFS storage classes

You can create and configure file systems quickly with **no minimum fee or setup cost**, and
**pay only for storage used**.

| Class group | What it offers |
|---|---|
| **Standard classes** — EFS Standard and EFS Standard-IA | **Multi-AZ resilience** and the **highest durability and availability**. Higher cost, because of that higher availability and durability |
| **One Zone classes** — EFS One Zone and EFS One Zone-IA | Data saved in a **single AZ** for **additional savings** versus the Standard classes |
| **Archive class** — EFS Archive | Cost-optimized for data accessed **a few times a year or less** that **doesn't need the sub-millisecond latency** of EFS Standard. Storage price up to **50% lower than EFS Infrequent Access** — for cold, rarely accessed data |

💡 Notice the **same three-way pattern as S3**: multi-AZ vs. one-zone, and hot vs. infrequent
vs. archive. Learn the pattern once and it transfers across services.

### EFS data lifecycle

Optimize costs further by **automatically moving data between storage classes based on usage
patterns**. Lifecycle policies determine when and how files transition between tiers,
**without manual intervention**:

| Policy | Default behavior |
|---|---|
| **Transition to IA** | Moves files into **Infrequent Access** (cost-optimized for data accessed a few times *each quarter*). **Default: files not accessed in Standard for 30 days** |
| **Transition to Archive** | Moves files into **Archive** (cost-optimized for data accessed a few times *each year* or less). **Default: files not accessed in Standard for 90 days** |
| **Transition to Standard** | Whether to move files **back** to Standard when they're accessed in IA or Archive. **Default: files are NOT moved back** — they stay in IA or Archive even when accessed |

⚠️ **That last default surprises people.** By default a file that goes cold and is later read
**stays** in the cheaper class. If you have files that go cold then suddenly get hot again,
you may want to turn "transition to Standard on first access" on.

## 8. Amazon FSx — managed third-party file systems

**Amazon FSx** makes it convenient and cost effective to **launch, run, and scale
feature-rich, high-performance file systems** in the cloud, supporting a wide range of
workloads with reliability, security, scalability, and a broad set of capabilities.

**📌 The key distinction from EFS:** EFS focuses on **NFS** compatibility. **FSx supports
multiple file system protocols** — **Windows File Server, Lustre, OpenZFS, and NetApp
ONTAP**.

FSx is built on the latest AWS compute, networking, and disk technologies for high performance
and **lower total cost of ownership (TCO)**. As a **fully managed service** it handles
**hardware provisioning, patching, and backups**.

### Benefits

| Benefit | ⬛ What it means |
|---|---|
| **File system integration** | You get the **real** file system — actual Windows SMB with Active Directory support, actual Lustre — so existing applications work unchanged, with no rewriting |
| **Managed infrastructure** | AWS handles hardware provisioning, patching, and backups. No file servers to build or maintain |
| **Scalable storage** | Grow capacity and throughput as needs change, without migrating to new hardware |
| **Cost effective** | A pricing model and **automated tiering** options that charge only for **used** storage and move **infrequently accessed data to lower-cost tiers** |

### The four file systems

| FSx flavor | Built on | Use cases |
|---|---|---|
| **FSx for Windows File Server** | Windows Server — fully managed shared storage with a wide range of data access, data management, and administrative capabilities | **Migrate Windows file servers to AWS** · Accelerate hybrid workloads · **Reduce SQL Server deployment cost** · Streamline virtual desktops and streaming |
| **FSx for NetApp ONTAP** | ONTAP's popular data access and management capabilities | **Migrate workloads to AWS seamlessly** · Build modern applications · Modernize data management · Streamline business continuity |
| **FSx for OpenZFS** | The OpenZFS file system, accessed via **NFS (v3, v4, v4.1, v4.2)** | Migrate workloads to AWS seamlessly · **Deliver insights faster for data analytics** · Accelerate content management · Increase dev/test velocity |
| **FSx for Lustre** | The Lustre file system's scalability and performance | **Accelerate machine learning** · **Enable high performance computing (HPC)** · Unlock big data analytics · Increase media workload agility |

### 🧒 ELI5 — the translator

Imagine you move to a new country, and your grandmother only speaks one very specific dialect.
You could teach her a new language (**rewrite your application for EFS**) — hard, slow, and
she'd probably get it wrong.

Or you could hire someone who **already speaks her exact dialect** (**FSx**). She keeps
talking exactly as she always has, and everything just works.

That's FSx: your Windows application wants to talk **SMB to a Windows file server**, so FSx
gives it a real Windows file server. Your supercomputer simulation wants **Lustre**, so FSx
gives it Lustre. **Nobody has to change how they speak.**

### 💡 Exam signals

| If the question says… | Answer |
|---|---|
| "Linux", "NFS", "shared across EC2 instances", "elastic" | **Amazon EFS** |
| "**Windows**", "SMB", "Active Directory", "migrate our Windows file server" | **FSx for Windows File Server** |
| "**machine learning**", "**HPC**", "highest-performance parallel file system" | **FSx for Lustre** |
| "NetApp", "ONTAP", "our existing storage vendor" | **FSx for NetApp ONTAP** |

## 9. AWS Storage Gateway — hybrid storage

**Storage Gateway** is a **hybrid cloud storage service** that seamlessly integrates
**on-premises environments with AWS Cloud storage**. It **extends your local storage to the
cloud while maintaining low-latency access to frequently used data**.

**Practical use cases:** moving **backups** to the cloud, on-premises **file shares backed by
cloud storage**, and **low-latency access to data in AWS for on-premises applications**.

### Benefits

| Benefit | ⬛ What it means |
|---|---|
| **Seamless integration** | Appears to your local systems as **standard storage** (a file server, an iSCSI disk, a tape library) — existing applications need no changes |
| **Improved data management** | Your on-premises data lands in S3, where **lifecycle policies, versioning, and cross-Region replication** apply to it like any other S3 data |
| **Local caching** | **Frequently used data is cached on-premises** for low-latency access while the full dataset lives in the cloud |
| **Cost optimization** | Stop buying and maintaining local storage arrays; pay for cloud storage you actually use, and tier cold data to Glacier |

### The three gateway types

| Gateway | Looks like… | What it does |
|---|---|---|
| **Amazon S3 File Gateway** | A **standard file server** (NFS/SMB) | Bridges your local environment with **S3**, giving on-premises applications virtually unlimited cloud storage **through familiar file protocols**. Files written to it are **automatically uploaded to S3**, while **intelligent caching** keeps recently used data locally. Applications keep working with files as they always have |
| **Volume Gateway** | **iSCSI volumes** your existing applications mount | Creates **virtual storage volumes** while maintaining local access. Two modes: **Cached** — primary data in the cloud, frequently accessed data cached locally for low latency. **Stored** — the **complete dataset stays local**, asynchronously backed up to the cloud as **EBS snapshots** |
| **Tape Gateway** | **Standard tape hardware** (a virtual tape library) | Replaces **physical tape infrastructure** with virtual tapes on AWS, working with **existing tape backup software**. Your backup software writes to virtual tapes as it would physical ones, **stored in S3** — and can automatically transition less frequently accessed data to a **more cost-effective storage class** for long-term retention |

### 🧒 ELI5 — the magic filing cabinet

Your office has a filing cabinet that everyone uses. It looks completely normal: same drawers,
same handles, same paper files.

But it's **secretly bottomless.** When you put a file in, it quietly gets copied to a giant
warehouse in another city. The cabinet keeps the files you've touched recently right there in
the drawer (**local cache**) so they're instant to grab. Ask for something from five years ago
and it's fetched from the warehouse.

Nobody in the office had to learn anything new. **They still just open a drawer.** That's the
whole point of Storage Gateway: it lies to your old software in a helpful way.

**The Volume Gateway modes, kid version:**
- **Cached** — the warehouse holds the real files; your drawer holds copies of the popular ones.
- **Stored** — your drawer holds the real files; the warehouse holds the backup copies.

**🏢 Real example of Tape Gateway:** a hospital has a 15-year-old backup system that writes to
physical tapes, and a compliance requirement to keep backups 10 years. Replacing the backup
software would cost a fortune. Instead they deploy a **Tape Gateway** — the software thinks
it's still writing to a tape robot, but the "tapes" land in S3 and age into **Glacier Deep
Archive**. No physical tapes, no courier to an offsite vault, no software rewrite.

## 10. AWS Elastic Disaster Recovery

**Elastic Disaster Recovery (DRS)** **replicates critical workloads to AWS with minimal
downtime.** Your servers' **block-level data is continuously replicated** to AWS, making it
ideal for uses needing robust disaster recovery. It supports **both physical and virtual
servers** for **rapid recovery during disruptions** — particularly valuable in industries like
healthcare where system availability is crucial.

It **reduces downtime and data loss** while **eliminating the costs of maintaining secondary
data centers**, and offers **non-disruptive disaster recovery testing** — it can quickly
launch recovery instances when needed.

### Benefits

| Benefit | ⬛ What it means |
|---|---|
| **Business resilience** | Continuous block-level replication means very little data loss and a fast recovery when the primary site fails |
| **Streamlined disaster recovery** | One managed service handles physical, virtual, and cloud servers, replacing hand-built scripts and runbooks |
| **Cost optimization** | **No idle secondary data center.** You pay for replication storage; the expensive recovery compute only launches during a test or a real disaster |

### Use cases

| Industry | Scenario |
|---|---|
| **Healthcare data protection** | Hospital systems replicate on-premises servers to AWS to **maintain compliance while protecting patient records**, ensuring critical medical data stays accessible during outages. **Regular DR testing** validates recovery procedures and meets strict healthcare regulations |
| **Financial services continuity** | A regional bank protects **core banking applications** by continuously replicating transaction processing systems, enabling quick recovery if the primary data center fails — maintaining customer trust and regulatory compliance |
| **Manufacturing operations recovery** | A global manufacturer protects **production planning systems** by replicating factory management servers to AWS, ensuring minimal disruption to supply chain operations during disasters. **Regular failover testing** validates the strategy |

### 🧒 ELI5 — the understudy

In a play, the lead actor has an **understudy** who watches every rehearsal and learns every
line **as it changes** (that's the *continuous replication*). The understudy doesn't stand on
stage — you're not paying for two actors to perform — they just sit in the wings, always
ready.

If the lead breaks a leg five minutes before curtain, the understudy walks on and the show
goes ahead. And crucially, the director **rehearses the swap regularly** (*non-disruptive DR
testing*) so that when it happens for real, nobody panics.

💡 **The financial argument, which the exam likes:** traditional DR means **buying and
maintaining an entire second data center** that sits idle 99.9% of the time. DRS replaces that
with cheap continuous replication and compute you only pay for when you actually fail over.

## 11. Choosing the right storage service

### The decision flow

```
 What are you storing?
 │
 ├── Files accessed over the web / by an application via API,
 │   backups, media, logs, a data lake
 │      └──────────────────────────────────────► Amazon S3
 │             (then pick a storage class by access pattern — §6)
 │
 ├── A disk for ONE EC2 instance (boot volume, database files)
 │      ├── Must it survive a stop/terminate?
 │      │      YES ──────────────────────────► Amazon EBS
 │      │      NO — it's scratch/cache ─────► EC2 instance store
 │      └──  (back EBS up with snapshots + Data Lifecycle Manager)
 │
 ├── A shared file system for MANY instances at once
 │      ├── Linux / NFS ─────────────────────► Amazon EFS
 │      ├── Windows / SMB / Active Directory ► FSx for Windows File Server
 │      ├── ML or HPC, extreme throughput ───► FSx for Lustre
 │      └── NetApp ONTAP or OpenZFS ─────────► FSx for that flavor
 │
 ├── On-premises systems that need cloud storage
 │   without changing the applications
 │      └──────────────────────────────────────► AWS Storage Gateway
 │             (file share → S3 File Gateway · iSCSI disk → Volume
 │              Gateway · tape backup software → Tape Gateway)
 │
 └── Replicating whole servers so you can recover
     them after a disaster
        └──────────────────────────────────────► AWS Elastic Disaster Recovery
```

### One-line cheat sheet

| Service | One-line identity | Kid version |
|---|---|---|
| **Instance store** | Temporary block storage on the host — **dies with the instance** | Hotel-room whiteboard |
| **Amazon EBS** | Persistent block volume for **one** instance, in **one AZ** | External hard drive |
| **EBS snapshots** | Incremental point-in-time backups, stored in S3 across AZs | Daily photos of your bedroom |
| **Amazon S3** | Object storage, **11 nines** durability, virtually unlimited | The world's biggest coat check |
| **S3 Lifecycle** | Rules that age objects into cheaper classes, then delete them | Moving toys floor → closet → attic → basement |
| **Amazon EFS** | Elastic **NFS** file system, **many** instances, **multi-AZ** | The family fridge |
| **Amazon FSx** | Managed **Windows / Lustre / ONTAP / OpenZFS** file systems | The translator who speaks your dialect |
| **Storage Gateway** | On-premises systems get cloud storage, no app changes | The bottomless filing cabinet |
| **Elastic Disaster Recovery** | Continuous server replication for fast recovery | The understudy |

### Cost intuition (cheapest → most expensive, per GB stored)

```
  Glacier Deep Archive  <  Glacier Flexible  <  Glacier Instant  <  One Zone-IA
     <  S3 Standard-IA  <  S3 Standard  <  EFS Standard  <  EBS gp3  <  EBS io2
  ──────────────────────────────────────────────────────────────────────────────►
  slower + cheaper                                        faster + more expensive
```

💡 And the rule that ties the module together: **the more machines can reach it at once, and
the faster it answers, the more it costs.** Instance store breaks the pattern by being both
fast and cheap — because it doesn't survive.

## 12. Quick recap + common exam traps

### Recap

- **Block** = a disk for one machine (**instance store**, **EBS**). **Object** = whole items in
  a flat namespace (**S3**). **File** = a shared hierarchy many machines mount (**EFS**, **FSx**).
- **Instance store dies** on stop/terminate; **EBS persists**. That contrast is the most
  tested thing in the module.
- **EBS is tied to one AZ** and attaches to **one instance**. **Snapshots** are incremental,
  stored in **S3 across multiple AZs**, and are how you move a volume to another AZ or Region.
- **Data Lifecycle Manager** automates snapshot creation, retention, and deletion.
- **S3**: objects in globally-uniquely-named buckets, **99.999999999% durability**,
  **private by default**. Secured with **bucket policies**, **identity-based policies**, and
  **encryption at rest and in transit**.
- **S3 storage classes** trade retrieval speed for price; **Intelligent-Tiering** picks for
  you; **S3 Lifecycle** automates **transition** and **expiration**.
- **EFS** = elastic, multi-AZ, NFS, many instances at once. **FSx** = the same idea but for
  **Windows, Lustre, ONTAP, and OpenZFS**.
- **Storage Gateway** (S3 File / Volume / Tape) makes cloud storage look like local storage.
  **Elastic Disaster Recovery** continuously replicates whole servers into AWS.
- Snapshot scheduling, cost monitoring, encryption, and **restore testing** are **your**
  responsibility under the Shared Responsibility Model.

### Traps

| Trap | The truth |
|---|---|
| "A reboot wipes the instance store" | **No** — a reboot keeps the same host, so data survives. **Stop** and **terminate** are what destroy it |
| "EBS volumes can be shared by several instances" | One volume, **one instance** (Multi-Attach is a narrow exception outside this course's scope). Need sharing? **EFS** |
| "An EBS volume can attach to any instance in the Region" | **Same AZ only.** Cross-AZ means snapshot → new volume |
| "Snapshots are full backups, so 10 snapshots = 10× the storage" | **Incremental.** Only changed blocks are stored, though **each still restores a complete volume** |
| "Deleting an old snapshot breaks the newer ones" | **No** — deleting removes only blocks **unique** to that snapshot; referenced data is preserved |
| "S3 has folders" | **Flat namespace.** `a/b/c.txt` is one key; the slashes are just characters |
| "S3 buckets are private only within my account" | Bucket **names are globally unique across all of AWS**; **contents are private by default** and must be explicitly granted |
| "Durability and availability are the same number" | **11 nines durability** (will it still exist) vs. **99.99% availability** (can I reach it now) |
| "Glacier always takes hours" | **Glacier Instant Retrieval is milliseconds.** Flexible is 1–5 min or 5–12 h; only **Deep Archive** defaults to 12 hours |
| "One Zone-IA is just a cheaper Standard-IA" | It's in **one AZ** — lose that AZ, lose the data. Only for **recreatable** data or secondary copies |
| "EFS needs to be provisioned and resized" | **Elastic** — it grows and shrinks automatically and you pay for what you use. **EBS** is what you provision |
| "EFS files return to Standard when accessed" | **By default they don't** — they stay in IA or Archive unless you enable the transition-to-Standard policy |
| "Use EFS for a Windows application" | EFS is **NFS/Linux**. Windows/SMB → **FSx for Windows File Server** |
| "Storage Gateway moves your data and you rewrite your apps" | The point is the opposite: it **looks like existing local storage**, so **applications don't change** |
